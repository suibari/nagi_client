# Design

## Context

動機と経緯は [proposal.md](proposal.md) のWhyを参照する。

- AppView（bsky-affirmative-bot、2026-11-12確認）は、生年月日の申告で18歳未満かつ `parentalConsent !== true` なら `parental_consent_required` で拒否し、受け付けたときは `parental_consent_at` に申告日時を保存している。
- クライアントは、申告フォームで18歳未満の日付が入力されたときだけ保護者の同意のスイッチを出し、サーバの拒否を「保護者の同意の確認が必要です」と表示する。
- プライバシーポリシーは、保護者の同意の日時を保存していることを記載していない。
- 民法上、未成年者が法定代理人の同意なしに結んだ契約は取り消しうる（民法5条）。規約から保護者の同意の一文を外すことの法的な扱いは、運営者の判断とする。

## Goals / Non-Goals

**Goals:**

- 外部の規約に由来する保護者の同意の要件を、表示・規約・サーバの検証から一貫してなくす。

**Non-Goals:**

- 年齢に応じた表示制御（未申告を未成年扱い、成人向けラベルの強制除外）の変更。
- 生年月日の申告を1度だけに限る仕組みの変更。

## Decisions

### D1: 文言・規約・サーバ検証を同時になくす

**課題**：規約から外しても、申告フォームやサーバの検証が残ると、利用者に存在しない要件の確認を求め続ける。

**採用判断**：ログイン画面、ゲスト投稿の同意文、申告フォーム、規約・ポリシー、AppViewの検証をすべて同じchangeで外す。

**理由と制約**：一部だけ残すと、規約と画面の説明が食い違う。AppViewの検証はクライアントより先に外す。逆の順だと、スイッチを外したクライアントから18歳未満の申告が拒否される。

### D2: クライアントは保護者の同意を送らない

**課題**：AppViewの入力型には任意の `parentalConsent` がある。

**採用判断**：クライアントは `parentalConsent` を送らない。`consent_required` のエラー分岐とその文言も削除する。

**理由と制約**：確認していない同意を `true` として送ると、事実と異なる記録を残す。AppViewの公開後は該当のエラーが返らない。

### D3: プライバシーポリシーの第5節の理由づけを削除する

**課題**：第5節は、保護者の同意が必要な理由を外部送信に結びつけている。2026-09-02に誤りと確認した理由づけである。

**採用判断**：段落ごと削除する。外部送信先と保持条件の説明は第5節・第6節に残る。

## Risks / Trade-offs

- 規約から外したことで、未成年の契約に関する定型の保護を失う → 運営者が判断済み。必要になれば別のchangeで戻す。
- AppViewとクライアントの公開に間がある → AppViewを先に出せば、旧クライアントのスイッチは送っても無視されるだけで害はない。

## Open Questions

- 既存の `parental_consent_at` の値を消すか（推奨：消す。今後は使わず、プライバシーポリシーにも記載がないため）。列の削除は別に行う。

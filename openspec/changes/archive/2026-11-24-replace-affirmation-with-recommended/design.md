# Design

## Context

- 全肯定フィードはAppViewの `getTimeline({ affirmation: true })` で、botたんのスコアが付いた投稿から1人1日1件（`dailyBestPerAuthor`）を時系列に並べている。会話のグループ化はしていない。
- 以前、埋め込みで閲覧者に近い投稿を混ぜる「動的枠」を全肯定フィードに入れていたが、候補が少なすぎて撤去した（本番実測で30日12件）。全肯定ニュースの動的枠は残っており、閲覧者の直近10件の投稿との最近傍距離で採点する（重心は全員に同じ記事が配られたため使わない）。
- 名刺の分析は新規登録時（`source: 'bluesky'`）にBlueskyの投稿100件といいね100件を読む。興味ジャンル（`actor_interest_genres`）と興味テーマはNagiの投稿だけから作っており、Bluesky由来の材料は分析のLLM入力として使った後に残していない。
- タブ設定はクライアントとAppViewの `parseFeedTabs` が同じ規則で検証し、`custom` の `source` は `affirmation` 以外を拒否している。クライアントは未知の `source` を既定へ寄せる。

## Goals / Non-Goals

**Goals**：読む人に合う投稿と反応が集まった投稿を、時系列のまま1人1日1件で見せる。Nagiで書く前の新規の人にも効かせる。

**Non-Goals**：スコア順の並び、おすすめの理由の表示、興味の手動編集、Blueskyの継続的な再取得。

## Decisions

### D1: 候補は「興味に近い」または「反応が集まった」、並びは時系列

候補を2つの条件の和集合にする。積集合や興味だけでは、過去に撤去した動的枠と同じく候補が尽きる。並びは新しい順に固定し、おすすめ度は1人1日1件の代表を選ぶときだけ使う。時系列なので既読位置（未読の目印）もそのまま使える。

代表選びは興味を優先する。興味に近い投稿（最近傍距離が閾値以内）があればその中で最も近いもの、無ければ反応した人数が最も多いもの、それも並べば新しいものを選ぶ。閾値より遠い投稿どうしの距離の差には意味が無いので、遠い投稿は反応で比べる。

反応の基準は5人とした（2026-11-24）。当初の2人では、開発DBのほぼすべての投稿に2人以上の反応が付いていて、おすすめがグローバルを1人1日1件に絞っただけになり、興味が並びにほとんど効かなかった。あわせて代表選びの順も反応優先から興味優先に改めた。

閾値は埋め込みモデルの較正表（`embeddingProfiles.ts` の `recommendDistMax`）に置く。検索の閾値と同じく、モデルを変えたら一緒に変わる値だからである。qwen3-embedding:0.6b では0.50とした（2026-11-24、開発DBで1人の直近10投稿と他人のトップ投稿2,564件を測定。最近傍距離の1%点が0.41、5%点が0.51、10%点が0.55。0.50までは同じ趣味や話題が並び、0.55を超えると挨拶や日常のひとことが混ざった）。検索と違って順位で打ち止めできず、閾値がそのまま候補の可否になるため、較正値のないモデルでは興味の候補を出さない側に倒す。

返信は候補にしない。おすすめは会話にまとめず1件ずつ並べるので、返信だけでは読めない。閲覧者本人の投稿も出さない。自分の投稿は自分の興味に必ず近くなるためである。

### D2: 興味の測り方はニュースの動的枠と同じ最近傍

閲覧者の材料ベクトル（最大10件）との最小コサイン距離で測る。重心を使わない理由はニュースの動的枠と同じ。材料はNagi投稿を優先し、足りない間はBluesky投稿の埋め込みを使う。

ジャンル（LLMで抽出した語）を突き合わせる案は、投稿ごとにジャンル判定のLLM呼び出しが要り、取り込みのたびにリクエスト外の処理が増える。埋め込みはNagi投稿ではすでに計算済みで、Bluesky投稿は登録時の1回だけ計算すればよいので、こちらを採る。

### D3: Bluesky由来の材料は埋め込みだけを持ち、置き換えたら消す

botの分析ジョブ（`source: 'bluesky'`）が読んだ投稿のうち、返信を除く直近10件を埋め込み、`nagi.actor_interest_probes`（仮称、did・埋め込み・作成日時）へ保存する。本文は保存しない。名刺の分析と同じく公開投稿だけを使い、いいねは他人の投稿なので材料にしない（名刺の分析で他人の趣味が混ざった過去の問題と同じ理由）。Nagiの埋め込み済み投稿が5件以上になったら削除する。

### D4: タブは `source: 'recommended'` を新設し、`affirmation` から読み替える

保存済みの `custom / affirmation` をそのまま「おすすめ」と解釈する案は、データと名前がずれ続けるので採らない。AppViewが先に `recommended` を受け付け、`affirmation` を読み替えるようにしてからクライアントを出す。旧クライアントは未知の `source` を `affirmation` へ寄せて全肯定APIを呼ぶため、全肯定APIは当面残す。組み込みタブのidは `recommended` とし、`?tab=affirmation` は別名として扱う。

### D5: 代表選びは日の境界で区切った範囲を1回ずつ採点する

全肯定と同じ「自分より良い兄弟が居なければ代表」というNOT EXISTSで書くと、兄弟ごとに反応人数と距離を計算し直すうえ、プランナが全投稿を走査するhash anti joinを選んだ（開発DB 1万件で約450ms、投稿数に比例して遅くなる）。そこで、JSTの日単位で範囲を切って範囲内の投稿を1回ずつ採点し、窓関数で1人1日1件の代表を選ぶ。1ページ分が埋まらなければ範囲を倍にする（7日から）。開発DBでは約60〜70msで、グローバルと同程度になった。

範囲は必ず日の境界で切り、カーソルはその後で当てる。カーソルの位置で日を途中から切ると、同じ日の新しい投稿が代表選びから抜け、ページをまたいで代表が変わる。材料のベクトルは先に読み、VALUESとしてクエリに埋め込む。

### D6: 未サインインの案内はおすすめにも出す

未サインインの人の最初のタブがおすすめになるため、これまでグローバルに出していた案内（showGuestHero）をおすすめにも出す。

## Risks / Trade-offs

- 母数が小さいため、興味の閾値や反応人数の基準しだいで候補が少なくなる。反応条件があるので、興味に合う投稿が無くても空にはなりにくい。リリース後に本番の件数を確認して閾値を調整する。
- 反応が集まる人気の書き手が毎日並びやすい。1人1日1件で上限をかける。
- Bluesky投稿の埋め込みを保存することになる。本文は保存せず、置き換えたら削除する。

## Migration Plan

1. lexiconに `getRecommended` と `source: 'recommended'` を追加する。
2. AppView・botを本番へ反映する（読み替え、API、興味ベクトル）。すでに登録済みの人のBluesky投稿は読み直さない。Nagi投稿が足りない間は反応条件の候補だけになる。
3. クライアントを反映する。

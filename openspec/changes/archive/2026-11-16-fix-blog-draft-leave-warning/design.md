# Design

## Context

動機と変更範囲は [proposal.md](proposal.md) に記載する。現在の新規作成のdirtyは入力の有無だけを見ており、lastSavedDraftKeyを参照しない。draftSnapshotとDraftContentは記事タイトル・タグを持たない。自動保存には本文必須の条件があり、メタデータだけの入力は保存されない。復元時は元の下書きを削除するため、復元しただけで保存済みと扱えない。

現行の設計判断は [ブログの設計](../../../specs/blog-publication/design.md) と [投稿の設計](../../../specs/post-composer/design.md) にある。導入時の固定証跡は両文書からリンクするcomment-snapshotを保持し、現行コードに合わせて書き換えない。

## Goals / Non-Goals

**Goals:** 保存応答で確認した復元可能な内容と現在の入力を比較し、実際に失われる内容があるかで新規ブログの離脱を判定する。

**Non-Goals:** 公開済み記事の編集判定の変更、画像blobの新たな永続化、PDSへの下書き公開は行わない。公開先とbot設定は従来どおり下書きの保存対象外で、復元時は既存の既定値・権限確認を使う。

## Decisions

### 保存した内容との比較を共有する

新規ブログでは本文・facet用参照・リンクカードの保存対象文字情報・タイトル・タグ等を、APIへ送る正規化済みスナップショットとして比較する。手動保存と自動保存を同じ経路で扱い、保存応答が確認できた内容だけを基準にする。単に保存成功フラグを立てる案では、保存中に追加入力した内容や、APIが捨てた追加フィールドまで保存済みになるため採用しない。本文のないメタデータ変更も自動保存対象にする。

現行drafts.saveは応答内容を呼出元へ返していないため、サーバが保持した内容を照合できるよう返り値を拡張する。AppViewの本人限定下書き契約に任意のブログメタデータ（articleTitle / articleTags）を追加し、旧データの欠落は空値として読む。API・lexiconの両方で任意文字列articleTitleと文字列配列articleTagsを定義する。既存の128KBの要求サイズ上限とバイナリ拒否を維持する。未知フィールドを送れたことだけでは保持を保証しない。

### 失われる画像と未保存内容を別の理由として扱う

離脱判定には、保存対象の差分と、復元できない添付画像を使う。本文で非表示になっていてもUndo用に保持している未永続化の画像は離脱で失われるため確認対象に含む。画像を残したまま本文だけ保存しても警告は解除しない。画面内の説明とアプリ内確認に画像を失う理由を示し、タブ閉鎖等の文言はブラウザ標準に従う。リンクカードのサムネイルは既存の再取得経路を利用する。

### 競合と所有者境界を保持する

保存中の変更は次の保存で照合する。セッション切替時は保存基準を無効にし、旧セッションの応答で上書きしない。下書き復元は現行どおり元を削除するので、復元後の再保存が完了して初めて警告を解除する。公開成功時の保存待ちと下書き削除、既存記事の編集時の比較は維持する。

## Risks / Trade-offs

- [別リポジトリのAPIがメタデータを保持しない] → サーバ側の保存・取得契約を先行対応する。旧応答で非空メタデータが欠ければ保存済み表示と警告解除をしない。モック検証と実APIの往復検証を区別する。
- [画像付きでは保存後も警告が残る] → 保存対象外である具体的な理由を示す。画像保存の追加はこのchangeの対象外とする。
- [復元時の元下書き削除後に通信が失敗する] → 未保存表示と離脱確認を維持する。元下書きを残す方式への変更は含めない。
- [保存待ち中の遅い応答] → 送信時の内容と所有者で照合し、現在の保存完了に読み替えない。

## Migration Plan

ユーザーの追加指定によりAppView側はOrcaワークツリー `/home/suibari/orca/workspaces/bsky-affirmative-bot/blog-draft-metadata`（`suibari/blog-draft-metadata`）で変更する。先にAppViewで任意メタデータの保存と返却、旧下書きの読取互換を整える。続いてクライアントの型・保存復元・離脱判定・文言を変更し、実APIでタイトル・タグの往復を確認する。外部リポジトリの対応が確認できない間は、完全対応済みと報告しない。クライアントのロールバックでは従来の警告に戻るが、追加フィールドや既存下書きを削除しない。本人限定の保存境界を維持し、新たな外部送信先は追加しない。

## 差分仕様の概要と参照先

| 分野             | 機能・要件                            | 主な利用の流れ                           |
| ---------------- | ------------------------------------- | ---------------------------------------- |
| blog-publication | 復元可能な下書きの離脱確認（BLOG-07） | 執筆、保存、離脱、復元                   |
| post-composer    | タイトル・タグの下書き保存（POST-06） | 入力、手動または自動保存、保存確認、復元 |

[ブログ主仕様](../../../specs/blog-publication/spec.md)の執筆条件と[投稿主仕様](../../../specs/post-composer/spec.md)のタイトル正本・片付け・画像互換を保持する。対応する差分は[ブログ](specs/blog-publication/spec.md)と[下書き](specs/post-composer/spec.md)に置く。公開プロトコルの変更はないため新たな外部プロトコル資料は追加しない。AppViewの外部実装の確認はtasks.mdで別途追跡する。

# Design

## Context

動機と変更範囲は [proposal.md](proposal.md) に記載する。現在のタブバーは4本以上で横スクロールに切り替えるが、スクロールバーを `scrollbar-width: none` で隠している。末尾の「＋」は sticky で右端に貼り付き、影で手前のタブを覆う。このため、続きがあることを示すものがない。利用者からのフィードバックは「7個目を設定しても横にスクロールしないから見れない」というものだった。開発者が確認したところ、PC・スマホともスクロール自体はできたので、問題は発見しやすさにあると判断した。

設定画面のプレビュー（`FeedTabPreview.svelte`）は同じ `.feed-tabs` クラスを使うが、タブは `button.feed-tab-preview-tab` である。実物の伸張規則（`a:not(.feed-tab-add)` への `flex-grow: 1`）と余白が当たらないため、収まる本数でも左寄せになる。

## Goals / Non-Goals

**Goals:** タブが何本あっても、すべてのタブに届くことが一目で分かり、PCのマウスでも届くようにする。プレビューを実物と一致させる。

**Non-Goals:** 上限本数の変更、タブの並べ替えUIの変更、‹ › 送りボタンの追加、タブの状態保持（FEED-02）の変更は行わない。

## Decisions

### 本数ではなく実測で入りきらないと判定する

画面幅・ラベルの長さ・言語によって収まる本数は変わる。そのため、ResizeObserverでバーの `scrollWidth > clientWidth` を見る。4本以上で横スクロールにする既存の切り替え（3本以下の等分は維持）はそのまま残す。「▾」を出す判定だけを実測にする。「＋」と「▾」は同じ幅にして、差し替えによって判定が揺れないようにする。

### 「＋」を「▾」に差し替え、カスタマイズは一覧の中に移す

入りきらないときに「＋」と「▾」を両方並べると、ただでさえ足りない幅がさらに減る。一覧の末尾にカスタマイズ項目を置けば、「＋」の役割は失われない。一覧は全タブを並べ、現在のタブに印を付ける。隠れているタブだけを並べる案は、スクロール位置によって中身が変わり分かりにくいため採らない。

### 送りボタンではなくフェードとホイールで補う

‹ › ボタンを付けると両端の幅が減り、一覧メニューと役割も重なる。フェードで続きを示し、PCのマウスにはホイールの縦回転を横送りに変換することで応える。ホイールを変換するのはバーがスクロールできる間だけで、端に達したらページのスクロールを妨げない。トラックパッドの横方向入力（deltaX）はそのままブラウザに任せる。

### プレビューは実物と同じ部品で描く

CSSの規則を2か所で揃え続けるのではなく、タブバーの描画部分を実物とプレビューで共有する。プレビューでの違いは、タブを押したときの動作（遷移ではなくプレビューの切り替え）と、sticky を外すことだけにする。プレビューの「▾」は見た目の確認用で、一覧は開かない。

## Risks / Trade-offs

- [ホイールの横変換が、ページを縦に読みたい操作を奪う] → 変換はバー上にポインタがあり、かつまだ送れる間だけにする。バーの高さは小さいので、読み進めの邪魔にはなりにくい。
- [フェードが短いラベルの読みやすさを下げる] → フェードは端の数十pxだけにし、隠れたタブがない側には出さない。
- [一覧メニューの開閉とフォーカス管理] → Esc・外側クリックで閉じ、「▾」にフォーカスを戻す。キーボードでも操作できることをE2Eで確認する。

## Migration Plan

クライアントだけの変更で、保存データやAPIには触れない。ロールバックすれば従来のタブバーに戻る。

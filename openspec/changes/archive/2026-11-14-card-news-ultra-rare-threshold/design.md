# Design

## Context

目的は [proposal.md](proposal.md) に記載する。`CardNewsList.svelte` は `getCardNews` の応答をそのまま保持し、日付見出し・空表示・追加読み込みを描画している。APIラッパーにはcursorとlimitがあり、レア度指定の契約はない。レア度の順序は型定義でN < R < SR < UR < AARと確認できる。

主仕様にニュースの取得レア度は未定義で、R以上という説明はコードコメントにある。これは既存要件違反の修正ではなく、CARD-10の追加として扱う。AppView側の選定処理はこのリポジトリでは確認していない。

## Goals / Non-Goals

表示対象だけを変更し、公開APIの互換性とページ順序を保つ。保存される控え、所持の権威、反応の権限は既存契約を維持し、新しい個人情報の取得や外部書き込みは追加しない。

## Decisions

### 表示前にカード取得項目だけを絞る

`cardGet` の `card.rarity` がURまたはAARの場合だけ表示対象とする。`zenkatsu` と `comboFound` はそのまま残す。UR以上と確認できないカード欠落項目も取得ニュースとしては出さない。抽出は初回・追加双方に共通して行い、日付見出しは抽出後の項目から組み立てる。

APIへの未定義パラメータ追加は避ける。AppViewで絞れば通信量も減るが、外部リポジトリの変更を必要とするため、今回の表示変更はクライアントで完結させる。

### cursorは表示件数と分けて保持する

除外した項目だけのページでもサーバのcursorを維持する。空表示の分岐の外に追加読み込み操作を置き、次ページに進めるようにする。自動で後続ページを連続取得せず、既存の明示的な操作を保つ。取得失敗の表示・再取得の挙動は現状に従う。

## Risks / Trade-offs

- [対象が少なく1ページが空になる] → cursorがあれば追加読み込み操作を残す。
- [サーバは引き続きR・SRを返しうる] → 全ページで同じ条件を適用する。AppView側の変更・本番検証は完了と主張しない。
- [R以上というコメントと新条件の不一致] → 実装時に周辺の重複説明を整理し、主仕様・design・known-gapsへ現状と確認境界を反映する。

## Migration Plan

データ移行は不要。クライアントの配信から過去分にも条件が適用される。戻す場合は表示の絞り込みを戻す。固定履歴 [コメント原文](../../../reference/comment-snapshot/cards-zenkatsu-advent.md) は書き換えず、主仕様の [設計判断](../../../specs/cards-zenkatsu/design.md) にある出典を維持する。

## 機能概要

カード取得ニュースの表示対象をUltra Rare以上に絞る。

## 機能一覧

| 機能           | 役割                                  | 要件    |
| -------------- | ------------------------------------- | ------- |
| カードニュース | UR・AARの取得と既存のハイライトを読む | CARD-10 |

## 主な利用の流れ

1. ゼンカツのニュースを開く。
2. 表示対象の取得ニュースとハイライトを読む。
3. 続きがあれば追加で読み込む。

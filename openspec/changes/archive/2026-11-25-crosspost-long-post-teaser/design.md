# Design

## Context

動機は [proposal.md](proposal.md) のWhyを参照する。

- 現行のクロスポストは、本文を300graphemes・3000bytesごとに分割し、2件目以降を直前の投稿への返信としてつなぐ（BSKY-05）。Bluesky投稿への返信・引用（BSKY-09）も同じ組み立てを使う。
- コピーはNagi保存後に作り、その強参照をNagi投稿の`crosspost`へ追記する（BSKY-06、[crosspost-after-nagi-save](../../crosspost-after-nagi-save/design.md)）。追記の時点でNagi投稿のCIDは変わる。AppViewはこの追記を編集とみなさない（API-09）。
- ブログ記事は分割せず、投稿通知と記事のリンクカードを1件だけ出している（BLOG-04）。
- mochottの実装（2026-11-24に公開レコードで確認）：
  - ZonePane v49から投稿された`app.bsky.feed.post`は、本文が冒頭＋`…もっと見る`で終わり、「もっと見る」に`https://mochott.site/{handle}/{rkey}`へのlink facetが付いていた。embedは通常の`app.bsky.embed.external`だった。
  - 同じレコードに追加フィールド`"site.mochott.longPost": { "uri": "at://{同じDID}/site.mochott.article/{rkey}", "cid": "..." }`があった。
  - lexicon `site.mochott.longPost`（`_lexicon.mochott.site`で公開）は、`uri`と`cid`を必須とする`object`である。「投稿は長文の冒頭で、全文は参照先の記事」という意味を持ち、参照先は投稿と同じリポジトリに限り、DIDが違えば読む側は無視すると定めている。
- Nagi AppViewはBlueskyの投稿を取り込まない（BSKY-01）。NagiのBlueskyタブは本人PDS経由で投稿を取得し、独自の表示型へ変換する。
- Nagi投稿は`com.suibari.nagi.getThread`でURIを指定して取得できる。こっそり・削除済み・モデレーションで隠れた投稿は、AppViewの判定どおり返らないか、隠れた状態で返る。

## Goals / Non-Goals

**Goals:**

- 長いNagi投稿のBlueskyコピーでタイムラインを埋めない。
- Bluesky公式アプリを含むどのクライアントでも、続きに辿り着けるようにする。
- 目印を読むクライアントでは、Nagiへ移らずに全文を読めるようにする。形はmochottと揃え、他のクライアントが対応しやすくする。

**Non-Goals:**

- mochottの目印の読み取り。
- 通常投稿のstandard.site化と、それによるBluesky公式アプリの拡張カード。
- 既存の分割コピーの作り直し。

## Decisions

### D1: クロスポストは冒頭＋本文中のリンクにする

上限を超える本文は、冒頭の末尾に`…もっと見る`を付け、「もっと見る」にNagiのスレッドページへのlink facetを張る。

検討した代替案：

- **分割を続ける**：Blueskyだけで全文を読める。ただしタイムラインを1本で埋める問題がそのまま残る。
- **Nagi投稿へのリンクカード（external）にする**：見た目で「続きがある」と分かる。ただしBlueskyでは画像・動画・引用とexternalを同時に付けられず、メディア付きの長文でカードを諦めるか、メディアを諦めるかになる。

本文中のリンクなら既存の埋め込み（BSKY-05）と衝突しない。mochottと同じ形なので、Blueskyの利用者にとって見慣れた導線になる。

リンク先は、引用先をリンクにするとき（BSKY-05、D9）と同じスレッドページとする。OGPはこっそり・ラベルの境界を守る（SEO-03）。

文言は利用者の表示言語で選ぶ（日本語は`…もっと見る`、英語は`…See more`）。記事ティーザーの投稿通知（BLOG-04）と同じ扱いである。

### D2: 冒頭の切り方は従来の分割の1件目と同じにする

従来の分割処理の先頭チャンクを使い、`…もっと見る`のぶんを上限から先に取り置く（記事ティーザーの抜粋と同じ手法）。改行→空白→grapheme境界の順に区切り、facetをまたがない。

画像付きの引用で引用先のURLを本文の末尾へ足す場合（BSKY-05）は、URLのぶんも取り置き、`…もっと見る`の後ろに空行で区切ってURLを置く。冒頭を切ったことで引用が消えるのを防ぐためである。

### D3: Bluesky投稿への返信・引用は分割を続ける

BSKY-09の投稿はNagi投稿を作らないので、続きを置く場所が無い。従来どおり分割して自分の返信へつなぐ。同じ処理の中で、Nagi投稿のURIを渡された場合（クロスポスト）だけ冒頭＋続きにする。

### D4: 目印は省略したときだけ、mochottと同じ形で書く

Blueskyコピーのレコードに、キー`com.suibari.nagi.longPost`で`{ uri, cid }`を入れる。`uri`は同じリポジトリの`com.suibari.nagi.post`、`cid`はコピー作成時に参照したNagi投稿の版とする。全文がBlueskyに載っているときは入れない。目印は「この投稿は全文の冒頭である」という意味なので、省略していない投稿に付けると意味が崩れる。

`app.bsky.feed.post`は未知のフィールドを許すので、レコードは受け付けられる（mochottの公開レコードで確認）。Bluesky公式アプリは無視する。

検討した代替案：

- **`cid`を任意にして`uri`だけを必須にする**：版のずれの問題は消える。ただしmochottの形から外れ、他のクライアントが両方に対応しにくくなる。
- **`crosspost`の追記を先に済ませてから目印を書く**：追記にはコピーのURIが要るので、順序上できない。

`cid`は`crosspost`の追記で必ず古くなる。lexiconに「クロスポストした時点の版」と明記し、Nagiは編集済みの判定にこのCIDを使わない（AppViewのAPI-09に従う）。

### D5: 読み取りは同じリポジトリのNagi投稿だけを対象にする

Blueskyタブの表示型へ変換するとき、目印の`uri`が投稿者と同じDIDの`com.suibari.nagi.post`を指す場合だけ取り込む。それ以外（DIDが違う、コレクションが違う、形が壊れている）は無視する。他人のNagi投稿を「自分の全文」と名乗らせないためである。

「全文を表示」を押したら`getThread`でNagi投稿を取得し、Bluesky投稿の本文の代わりにNagi投稿の本文とfacetを表示する。Nagi AppViewへ渡すのはNagi投稿のURIだけで、BlueskyのURIは渡さない（BSKY-01）。取得できない、または隠れた状態で返った場合は、冒頭のまま「全文を表示できませんでした」と伝える。「もっと見る」のリンクは残るので、Nagiで開く導線は失われない。

取得結果はその画面の表示にだけ使い、アカウントを切り替えたら捨てる。

## Risks / Trade-offs

- [Blueskyだけで全文を読めなくなる] → 続きは、引用先をリンクにするとき（BSKY-05）と同じスレッドページで読める。未ログインでどこまで読めるかは既存のスレッドページの扱いに従い、この change では変えない。こっそり投稿はそもそもクロスポストしない（BSKY-04）。
- [冒頭の切れ目が文の途中になる] → 従来の分割と同じ区切り規則なので、1件目の見え方は今と変わらない。
- [`cid`が常に1つ古い] → D4のとおりlexiconに明記する。CIDを比べて「編集された」と表示するクライアントでは、編集していなくても編集済みに見える可能性がある。mochottの記事も更新で同じことが起きるので、相互運用上は許容する。
- [Nagi投稿を消すとリンク切れになる] → 削除時に「Blueskyのコピーも削除する」を選べる（BSKY-10）。選ばなかった場合は、従来の分割コピーと同じくBluesky側が残る。
- [lexiconの公開前に目印を書く] → `app.bsky.feed.post`は未知のフィールドを許すので、書き込みは失敗しない。公開は読む側の利便のためで、フェーズ2の前に済ませる。

## Migration Plan

1. フェーズ1：クライアントで冒頭＋続きの1件に切り替える。lexicon・AppViewの変更は要らない。
2. lexicon（bsky-affirmative-bot）に`com.suibari.nagi.longPost`を追加し、`com.atproto.lexicon.schema`として公開する。
3. フェーズ2：クライアントで目印の書き込みと読み取りを出す。
4. ロールバックはクライアントの差し戻しで行う。既に作ったコピーと目印は残るが、無害である。

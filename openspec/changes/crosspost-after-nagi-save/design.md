# Design

## Context

動機は [proposal.md](proposal.md) のWhyを参照する。

- 現行の通常クロスポストはBlueskyのコピーを先に作り、その強参照（`crosspost`）を最初のNagiレコードへ入れる。Nagi保存が失敗すると、作成済みのコピーを削除しようとする。分割投稿の途中で失敗した場合も、作成済みの分を削除しようとする。
- Bluesky投稿の権限は `repo:app.bsky.feed.post?action=create` に限っている。そのため削除は拒否されうる。旧セッションに広い権限が残っている場合は成功することもあり、結果が一定しない。
- 通常投稿の編集（`updatePost`）は既存レコードを読み、未知のフィールドを含めて引き継いだうえで上書きする。レコードに編集日時のフィールドは無く、AppViewは更新の取り込みそのものを編集と判断していると考えられる。AppViewの実装は別リポジトリにあり、このリポジトリからは確認していない。
- 記事のティーザーは公開URLが要るため、すでに記事作成後に投稿している。

## Goals / Non-Goals

**Goals:**

- Bluesky投稿の権限をcreate限定に保ったまま、削除による補償を不要にする。
- Nagi投稿の成否をBlueskyの成否に左右させない。Nagiが正本で、Blueskyはその写しである。
- AppViewの編集判定を、付帯情報の例外ではなく「見える内容の変化」という一般的な定義で表す。

**Non-Goals:**

- 過去に作られた孤立コピーの検出や掃除。
- Bluesky側のコピーにNagiのURLを載せること。順序変更で可能にはなるが、別のchangeで扱う。
- 投稿編集（`updatePost`）の楽観ロック化。

## Decisions

### D1: Nagi保存 → Bluesky作成 → 参照追記の順にする

Nagi投稿を作成したら、その内容でBlueskyのコピーを作る。全件そろったら、Nagi投稿へ `crosspost` を追記する。

検討した代替案：

- **今の順序のまま削除処理だけ外す**：最小の修正で済む。ただしNagi保存に失敗すると、Blueskyにだけ投稿が残る。正本が無い写しを作りうる構造そのものが残る。
- **BlueskyのrkeyとCIDを事前に決めてNagiの初回レコードへ入れる**：削除権限も追記も要らない。ただし、Bluesky側のレコード内容が1バイトでも違えばCIDがずれ、参照が壊れる。分割投稿では親のCIDを順に計算する必要もある。正しさをCBORの符号化の一致に頼るため壊れやすい。
- **連携を別レコード（例：`com.suibari.nagi.crosspost`）で表す**：投稿本体を書き換えないので、編集判定の問題もCIDの問題も根本から起きない。atprotoらしい形だが、lexiconの追加、AppViewでの取り込みと結合、既存の `crosspost` フィールドとの二重対応が要る。今回の問題に対しては変更量が大きすぎる。

採用案は、AppViewの編集判定の見直し（D2）と組み合わせることで変更量を抑えつつ、正本が先・写しが後という順序を保てる。

### D2: AppViewの編集判定を「見える内容の差分」で行う

AppViewは、更新を取り込むときに直前の取り込み済みレコードと内容フィールドを比べる。差分がある場合だけ編集として扱い、編集済みの表示・翻訳・bot判定・通知をやり直す。内容フィールドに差分が無い更新は、付帯情報だけを最新のレコードへ反映する。契約は [API-09](specs/appview-protocol/spec.md) に定める。

内容フィールドは列挙して管理する（本文、facets、embed、linkCards、langs、CW、labels、記事の見出し等）。新しいフィールドを分類し忘れると、内容の変更が編集として扱われない側へ倒れる。そこでAppViewには、lexiconの全フィールドが「内容」か「付帯」のどちらかに分類済みであることを確かめるテストを置く。

`crosspost` だけを編集判定から外す例外は採らない。理由は、付帯情報が増えるたびに例外が積み上がり、編集の意味がフィールドの一覧でしか説明できなくなるためである。

### D3: 参照追記は作成時のCIDを条件に書き込む

追記は `putRecord` に `swapRecord`（作成直後のCID）を付けて行う。投稿者がその間に編集してCIDが変わっていた場合は、最新のレコードを読み直し、`crosspost` だけを足して1回だけ再試行する。それでも失敗した場合は、参照追記の失敗として警告を出す。追記後は通常の書き込みと同じくensureRecordで取り込みを促す。

### D4: 分割投稿が途中で失敗したら参照を追記しない

途中までのスレッドをNagi投稿のコピーとして登録すると、Nagi上でそのコピーへ返信や引用を続けたときに、内容の欠けた写しの続きになってしまう。そのため参照は追記せず、Blueskyに途中までのコピーが残ったことだけを警告で伝える。作成済みの分は、権限の方針どおり削除しない。

### D5: 失敗はすべて警告で伝え、Nagi投稿を成功として扱う

Blueskyの作成失敗、分割の途中失敗、参照追記の失敗は、いずれもNagi投稿の成功を取り消さない。利用者には、どこまでBlueskyに出たかが分かる文言を出す。

## Risks / Trade-offs

- [AppViewの対応より先にクライアントを出すと、全クロスポストが編集済みになり、翻訳・判定・通知が二重に走る] → AppViewを先に本番へ反映し、その動作を確認してからクライアントを出す（Migration Plan参照）。
- [参照追記の前後で投稿のCIDが変わり、その数秒間にされた返信・引用が古いCIDを指す] → atprotoでは古いCIDへの参照は通常起きることとして扱う。AppViewが返信・引用の取り込み時にCIDの一致を必須にしていないかを、AppView側の作業で確認する。
- [追記が終わるまでの数秒間、その投稿への返信をBlueskyへ続けられない] → BSKY-04の「コピーを参照できない場合は外部化しない」既存の扱いに入るので、孤立した返信は作られない。許容する。
- [参照追記の前に読んだ内容で編集が上書きすると、追記した参照が消える] → 送信処理の中で追記まで行うので、この時間帯はほぼ無い。編集処理の楽観ロック化はNon-Goalとし、起きた場合はクロスポストの続きが作れなくなるだけで、内容は失われない。
- [Blueskyのコピーの作成時刻がNagi投稿より数秒遅れる] → コピーの `createdAt` は従来どおりNagi投稿の作成時刻を基準にする。

## Migration Plan

1. AppViewでD2の編集判定を実装し、テストとともに本番へ反映する。参照だけを追記した投稿が編集済みにならないことを、本番で1件確認する。
2. クライアントの順序変更と削除処理の除去を出す。
3. ロールバックはクライアントの差し戻しで行う。AppView側の判定変更は従来の投稿にも無害なので、差し戻さなくてよい。

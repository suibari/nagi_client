# 通知・Web Push・既読位置

## Purpose

### 機能概要

利用者が返信やリアクションなどの出来事に気付き、読んだ状態を複数端末でも矛盾なく扱えるようにする。アプリ内の通知一覧・未読数・アイコンバッジに加え、閉じたPWAにもWeb Pushで通知する。

通知の種別設定はアカウント単位、Push購読は端末単位である。フィードやニュースの「ここまで読んだ」位置は通知件数とは別の仕組みで、それぞれ必要な範囲だけ同期する。

### 機能一覧

| 機能                 | 役割・利用者ができること                               | 詳細要件                                          |
| -------------------- | ------------------------------------------------------ | ------------------------------------------------- |
| 通知内容の設定       | 種類ごとの一覧・Pushの有効無効をアカウントへ保存する。 | [NOTIFY-01](#notify-01)                           |
| 一覧・件数・バッジ   | 新着を取得し、画面に出せた範囲だけを既読にする。       | [NOTIFY-01](#notify-01) / [NOTIFY-02](#notify-02) |
| 起動時の優先取得     | 認証復元直後に件数取得を先行し、応答をすぐ表示する。   | [NOTIFY-06](#notify-06)                           |
| 端末の購読・解除     | 対応環境で許可を取り、端末とAppViewへ購読を登録する。  | [NOTIFY-03](#notify-03)                           |
| 配信経路の修復       | 端末だけ購読済みの状態や鍵の更新に対応する。           | [NOTIFY-03](#notify-03) / [NOTIFY-05](#notify-05) |
| バックグラウンド通知 | 旧payloadも受け取り、クリックで対象画面へ移動する。    | [NOTIFY-04](#notify-04) / [NOTIFY-05](#notify-05) |
| セクション既読       | 画面の既読位置を単調に進め、DID別に同期する。          | [UNREAD-01](#unread-01) / [UNREAD-02](#unread-02) |

### 主な利用の流れ

1. 利用者が端末でPushを許可し、購読をAppViewへ登録する。種類設定は別にアカウントへ保存する。
2. AppViewが配信を判断し、SWがOS通知を出して開いている画面にも知らせる。
3. 通知を開くと対象へ移動し、表示できた最新分まで既読にする。
4. 起動時はOAuth復元直後に通知件数取得を他のセッション依存の初回取得より先に開始する。応答を待たず他の読み込みも進め、取得できた件数をすぐ表示する。
5. 起動・復帰時に購読登録と正確な未読数を取り直し、端末とサーバーのずれを修復する。

この文書は現行クライアントの振る舞いを整理する。設計判断は [design.md](design.md)、導入時の証跡は [コメント原文](../../reference/comment-snapshot/notifications-unread.md)、既知の不整合は [known-gaps.md](../../known-gaps.md) に分けて記録する。シナリオは確認条件であり、全外部環境での実行合格を示すものではない。

## Requirements

<a id="notify-01"></a>

### Requirement: NOTIFY-01 一覧・Push設定と件数

通知設定はアカウント単位でAppViewが一覧・未読・Pushの全てへ適用しなければならない（MUST）。UIの1トグルはlist/pushの両方へ同じ値を書き、未設定は有効とする。通知件数の正本はサーバのreadAtで、別のローカル通知既読を作らない。

#### Scenario: トグル変更

- **WHEN** 通知種別をオフにする
- **THEN** 設定全体を送信しlistとpushを揃える

#### Scenario: 設定保存失敗

- **WHEN** 楽観的に切り替えたAPIが失敗する
- **THEN** 見た目を戻し、保存中の並行変更を止める

<a id="notify-02"></a>

### Requirement: NOTIFY-02 読み直しと既読の上限

一覧はOAuth復元後、初回・画面復帰・ナビ再タップで再取得し、表示できた最新createdAtまで既読にしなければならない（MUST）。取得後に到着した未表示通知まで消さない。未読取得は60秒・復帰・Push受信で行い、既読化前の古い応答を世代で捨てる。

#### Scenario: 一覧表示中の新着

- **WHEN** 取得後に通知が到着する
- **THEN** 表示していない通知をseenAtへ巻き込まない

#### Scenario: 再取得失敗

- **WHEN** 既存一覧がある状態で通信が落ちる
- **THEN** 一覧を消さず次回へ残す

<a id="notify-03"></a>

### Requirement: NOTIFY-03 端末購読とサーバ登録の分離

ブラウザ購読意思とAppView登録成功は別状態で保持しなければならない（MUST）。端末に購読があれば起動・復帰等で冪等再登録し、サーバ一時失敗だけで端末の意思をOFFにしない。解除が端末で成功したら表示をOFFに保つ。iOS非standalone等の非対応環境では理由を案内する。

#### Scenario: 端末だけ購読済み

- **WHEN** AppViewの購読行が失われる
- **THEN** 次の同期で再登録して自己修復する

#### Scenario: 再登録の一時失敗

- **WHEN** ブラウザの購読は有効
- **THEN** 購読意思を保持し復帰時の再試行に委ねる

<a id="notify-04"></a>

### Requirement: NOTIFY-04 Service Workerの互換性

SWはキャッシュを担当せずPush受信・クリック・購読更新を薄く担当しなければならない（MUST）。payloadは全項目optionalで旧サーバ/旧SWを扱う。tag欠落時は一意な値を作り、同種通知の上書き消失を防ぐ。skipWaitingとclients.claimで更新を反映する。

#### Scenario: tag無しの連続通知

- **WHEN** 同じtypeの通知が2通届く
- **THEN** typeをtagに流用せず両方を気付ける通知にする

#### Scenario: アプリ表示中の受信

- **WHEN** SWがPushを表示する
- **THEN** 開いているタブへ合図し未読件数を即時再取得する

<a id="notify-05"></a>

### Requirement: NOTIFY-05 installation capabilityと遷移

SWの購読更新はDIDを変更できない端末固有capabilityを使い、失敗時はブラウザの認証済み修復へ引き継がなければならない（MUST）。クリック時は既存windowへfocusして遷移し、無ければ新規に開く。通知種別とsubjectに応じて記事・日記・年表・カード等の正しい画面へ送る。

#### Scenario: 購読鍵の更新

- **WHEN** SWだけでpushsubscriptionchangeを受ける
- **THEN** 同じ受取人の購読だけを更新する

#### Scenario: 無関係の付随post

- **WHEN** 通知subjectと別postが付く
- **THEN** そのpostの記事属性でsubjectの遷移先を変えない

<a id="notify-06"></a>

### Requirement: NOTIFY-06 起動時の通知件数の優先取得

クライアントは、リロード時に復元されたOAuthセッションで認証付き通信が利用可能になり次第、他のセッション依存の初回データ取得より先に通知件数取得を開始しなければならない（MUST）。他の取得は通知の応答を待たず進め、正常な件数応答を受信したら直ちにナビゲーションと対応するPWAバッジへ反映する。認証復元前に本人用件数を取得せず、旧セッションや既読化前の古い応答を適用してはならない（MUST NOT）。

#### Scenario: リロード後の取得開始順

- **WHEN** リロード後にOAuthセッションが復元される
- **THEN** プロフィール、フィード、設定などのセッション依存の初回取得より先に通知件数取得を開始する
- **AND** 他の取得が未完了でも、通知件数の正常応答を受けた時点でバッジへ反映する

#### Scenario: 通知取得が遅い場合

- **WHEN** 起動時の通知件数取得が応答待ちになる
- **THEN** フィードなどの初回取得と表示はその応答を待たずに進む

#### Scenario: 通知取得が失敗する場合

- **WHEN** 起動時の通知件数取得が通信または認可エラーで失敗する
- **THEN** 他の初回取得を止めず、既存の再試行と定期取得に委ねる

#### Scenario: 未ログインでの起動

- **WHEN** OAuth復元後もセッションがない
- **THEN** 本人用通知件数の取得を開始しない

#### Scenario: 別アカウントへの切替

- **WHEN** アカウントAの件数取得中にBへ切り替える、またはログアウトする
- **THEN** Aの応答を切替後のバッジへ反映せず、BではBの件数を取得する

#### Scenario: 取得中に通知を既読にする

- **WHEN** 起動時の件数取得中に表示済み通知の既読化が完了する
- **THEN** 既読化より前に開始した応答で件数を巻き戻さない

<a id="unread-01"></a>

### Requirement: UNREAD-01 セクション既読の単調性

セクション既読はindexedAt DESC, uri DESCの順で比較し、新しい方へだけ進めなければならない（MUST）。初利用端末は現在位置を既読基準とし、表示ビューは開いた時点の基準を凍結する。空のindexedAtは位置に使わない。localStorage失敗時もメモリ状態を維持する。

#### Scenario: 別端末の古い位置

- **WHEN** 現在より古いremoteを受信する
- **THEN** 既読を後退させない

#### Scenario: 表示中の既読化

- **WHEN** 最新表示分まで保存位置を進める
- **THEN** 凍結したビューの未読マークは消さない

<a id="unread-02"></a>

### Requirement: UNREAD-02 スコープと同期の分担

セクションは1インスタンスへ集約し、DID変更時に作り直さなければならない（MUST）。news等のアカウント同期と端末だけのfeed既読を区別する。guestはサーバへ送らず、remote取り込みは反射送信しない。全削除時は生きたインスタンスも破棄して消したキーを書き戻させない。

#### Scenario: サインアウト中の既読

- **WHEN** guestがニュースを読む
- **THEN** 本人の既読へ混ぜず端末内へ閉じる

#### Scenario: 全データ削除後

- **WHEN** 旧watermarkがメモリに残りうる
- **THEN** インスタンスを捨てて保存値の復活を防ぐ

# フィード・タブ・スレッド・リアクション

## Purpose

### 機能概要

利用者が投稿を読み、会話の流れを追い、返信やリアクションで応答する画面群である。ホーム・グローバル・タグ・検索などをタブで切り替えられ、行き来しても読んでいた状態を保つ。会話の重複や投稿後の見失いを防ぎ、書いた結果が同じ画面で自然に分かることを目的とする。

取得対象の可視性は既存AppView APIが決める。Blueskyのタブは同じ画面基盤を使うが、データ取得と操作の境界は別仕様である。

### 主な利用の流れ

1. フィードまたは検索を開き、読みたいタブを選ぶ。
2. キャッシュ済みの内容を表示し、必要に応じて新しい結果や続きを取得する。
3. 会話を展開したりスレッドへ移り、返信・引用・リアクションを行う。
4. 操作結果を即時反映し、確定データへ置き換わった後も対象の投稿へ案内する。
5. 未ログインで共有された公開投稿を開いたときは、会話の後ろの紹介からNagiに参加できる。

この文書は現行クライアントの振る舞いを整理する。設計判断は [design.md](design.md)、導入時の証跡は [コメント原文](../../reference/comment-snapshot/feed-thread.md)、既知の不整合は [known-gaps.md](../../known-gaps.md) に分けて記録する。シナリオは確認条件であり、全外部環境での実行合格を示すものではない。

## Requirements

<a id="feed-01"></a>

### Requirement: FEED-01 タブと旧リンク

フィードは設定されたタブと?tab=idで選択し、取得経路・可視性は既存APIに従わなければならない（MUST）。不正タブだけを捨て、旧channel/tag検索タブはhashtagへ移す。全て無効な場合だけ既定へ戻す。既定のタブは「おすすめ / ホーム / グローバル」の順とし、未サインイン・新規・タブを保存していない人は一番左のおすすめを最初に見る。保存済みの全肯定タブは同じ位置でおすすめタブとして読み、`/affirmation` と `?tab=affirmation` の旧リンクはおすすめを開く。廃止チャンネルの旧URLはPDSから名前を読みタグページへ案内する。Blueskyのフィードのタブには、タブバーと一覧のメニューでBlueskyのアイコンを付け、Nagiのタブと見分けられるようにする（2026-11-22に合意）。

#### Scenario: 一部の設定破損

- **WHEN** 保存タブに読めない要素が1つある
- **THEN** 有効な残りの並びを保持する

#### Scenario: 旧チャンネルURL

- **WHEN** 以前共有したチャンネルを開く
- **THEN** 廃止APIを呼ばずタグ検索へ移す

#### Scenario: Blueskyのフィードのタブ

- **WHEN** NagiのタブとBlueskyのフォロー中やカスタムフィードのタブを並べている
- **THEN** Blueskyのタブにだけ名前の前にBlueskyのアイコンを付け、読み上げでもBlueskyのタブだと分かるようにする

#### Scenario: 未サインインで初めてフィードを開く

- **WHEN** 未サインインの人が `/feed` を開く
- **THEN** 一番左のおすすめタブを選んだ状態で表示する

#### Scenario: タブを保存していないサインイン済みの人

- **WHEN** タブをカスタマイズしたことのない人がフィードを開く
- **THEN** 「おすすめ / ホーム / グローバル」を並べ、おすすめを選んだ状態で表示する

#### Scenario: 全肯定タブを保存している人

- **WHEN** 保存したタブに全肯定タブが含まれる
- **THEN** 同じ位置におすすめタブを表示し、他のタブの並びは変えない。おすすめタブも保存済みならおすすめは1つだけにする

#### Scenario: 全肯定の旧リンク

- **WHEN** `/affirmation` または `/feed?tab=affirmation` を開く
- **THEN** おすすめタブを開く

<a id="feed-02"></a>

### Requirement: FEED-02 キャッシュとアカウント境界

タブ状態は共有LRUに保持し、プレビューのpeekでは新規作成や最近使用順の変更で表示中タブを追い出してはならない（MUST）。DIDを含むキーを使い、アカウント変更時は旧キャッシュを捨てる。ナビ再タップ・復帰も共通の更新経路を使う。

#### Scenario: アカウント切替

- **WHEN** 本人向けフィードがキャッシュ済み
- **THEN** 前の人の内容を残さず取得し直す

#### Scenario: スワイプ覗き見

- **WHEN** 隣タブのキャッシュを読む
- **THEN** 表示中タブのLRU寿命を壊さない

<a id="feed-03"></a>

### Requirement: FEED-03 会話の安定キーと更新位置

会話は代表uriが変わってもthreadRootUriを安定キーにし、同一スレッドの重複を防がなければならない（MUST）。新返信と自分の投稿を含む会話はサーバが返す位置へ挿し直す。削除は現在タブだけでなくキャッシュ全体へ伝播する。

#### Scenario: 新返信が到着

- **WHEN** 会話カードの代表投稿uriが変わる
- **THEN** 同じ会話を二重に表示しない

#### Scenario: 別タブでの削除反映

- **WHEN** 投稿を削除してタブを切り替える
- **THEN** キャッシュ済みタブでも削除を反映する

<a id="feed-04"></a>

### Requirement: FEED-04 楽観表示と追従

新規投稿・返信は楽観表示から確定表示へ置き換え、DOM差し替え後も発言単位で追従しなければならない（MUST）。投稿完了の共有signalは確定情報への更新に使う。編集直後は即時fetchで古い本文に戻さず、楽観変更を取り込みへ収束させる。

#### Scenario: ネスト返信の確定

- **WHEN** 楽観バブルが実URIと会話カードへ置き換わる
- **THEN** 返信の位置を再探索して見失わない

#### Scenario: 編集直後

- **WHEN** PDS保存は完了しAppView取り込みがまだ
- **THEN** 旧内容で楽観編集を打ち消さない

<a id="feed-05"></a>

### Requirement: FEED-05 プレビューとbot返信の折り畳み

タイムラインの会話プレビューはルートと末尾3返信を残さなければならない（MUST）。折り畳み候補は他人のトップ投稿へのbotの直接返信に限り、メディア付き・人の返信があるbot返信・自分のルートは残す。人の返信の有無をスレッド取得で確かめる間も、折り畳み候補は折り畳んで表示し、確認で残すと分かった返信と確認に失敗した返信を展開する。確認取得は閲覧者とルートごとに共有し、短期キャッシュの無効化後に古い応答を再登録しない。

#### Scenario: 画像付きbot返信

- **WHEN** 他人のトップ投稿にbotが画像を返す
- **THEN** 折り畳まず見せる

#### Scenario: 自分の投稿への返信

- **WHEN** 自分のトップ投稿にbotが返す
- **THEN** 他人向けの省略規則を適用しない

#### Scenario: 確認中のbot返信

- **WHEN** おすすめフィードなど会話グループ形式でない項目を開き、bot返信に人の返信があるかを確認している
- **THEN** 折り畳み候補のbot返信を最初から「botたんの返信を表示」に折り畳んで表示する
- **AND** 確認で人の返信があると分かったら展開する

#### Scenario: 確認の取得に失敗する

- **WHEN** 人の返信の有無を確かめるスレッド取得が失敗する
- **THEN** 折り畳み候補のbot返信を展開して表示する

<a id="feed-06"></a>

### Requirement: FEED-06 あなたへ・返信深度・こっそりURI

あなたへの目印は本人の投稿への他人の直接返信に付けなければならない（MUST）。作者はカード内の親投稿から求め、AppView DID配下のこっそりURIを作者DIDと誤認しない。深度計算は欠落・循環参照でも止めず、取得できた範囲を使う。

#### Scenario: こっそりへの返信

- **WHEN** 親URIのDIDがAppViewを指す
- **THEN** URIから本人の投稿と断定せず実際の親作者で判断する

#### Scenario: 親参照の循環

- **WHEN** 壊れた返信チェーンを描画する
- **THEN** 無限ループにせず描画可能な深度を返す

<a id="feed-07"></a>

### Requirement: FEED-07 リアクションと投稿表示

リアクションの所有者・対象・操作可能性は投稿やニュース等の実体に従い、合成表示のURIへ誤送信してはならない（MUST）。読み取り専用表示やゲストサンプルに実データ変更を伴わせない。本文省略・画像枚数・リンクカード枚数は各表示の契約に従い、記事と3行日記の添付を二重表示しない。

#### Scenario: 3行日記表示

- **WHEN** 各行の下に画像を表示する
- **THEN** 同じ画像を本文下ギャラリーへ重複して出さない

#### Scenario: メディアタブ

- **WHEN** 複数画像を持つ同一スレッドを表示する
- **THEN** 会話グループ化で画像を失わず投稿単位のタイルへ展開する

<a id="feed-08"></a>

### Requirement: FEED-08 スワイプと検索

スワイプは距離・速度で確定しなければならない（MUST）。フィードの画像タイル上でも本文と同じ横スワイプでタブを移動できる。画像タイルのタップは拡大表示し、横ドラッグを認識した操作では、移動確定・元へ戻る・中断のいずれでも画像の拡大やリンクの起動を伴わせない。縦操作はブラウザへ委ねる。拡大ビュー、動画・音声、画像の警告操作、その他の操作部品と内部スクロール領域のジェスチャは奪わない。idle時はtransformを外しfixed要素を壊さない。検索の一致結果は公開タブ分を先に読み件数を示し、埋め込みが必要な気まぐれ検索は開いたタブだけ遅延取得する。

#### Scenario: 隣タブなし

- **WHEN** 終端からさらにスワイプする
- **THEN** 抵抗を示して元へ戻す

#### Scenario: 既定検索タブ0件

- **WHEN** 別の公開タブには一致がある
- **THEN** タブ件数で別の結果があることを示す

#### Scenario: 画像上からタブを移動

- **WHEN** タブスワイプが有効なモバイル画面で、NagiまたはBluesky投稿の画像タイル上から隣タブ方向へ確定条件を満たす横スワイプを行う
- **THEN** 本文上と同じプレビューとタブ移動を行い、画像やリンクを開かない

#### Scenario: 画像のタップ

- **WHEN** 画像タイルを横ドラッグせずタップする
- **THEN** 従来どおり画像を拡大表示する

#### Scenario: 短い横ドラッグと中断

- **WHEN** 画像上で横ドラッグを認識した後、確定条件を満たさず離すか、複数指またはtouchcancelで中断する
- **THEN** 元のタブへ戻り、画像やリンクを開かない。次の独立したタップでは画像を開ける

#### Scenario: 画像上の縦スクロール

- **WHEN** 画像上から縦方向に指を動かす
- **THEN** ページの縦スクロールを妨げず、タブを切り替えない

#### Scenario: 独立した操作の保護

- **WHEN** 拡大ビュー、動画・音声、警告の解除・再非表示、通常のリンクやボタン、内部スクロール領域を操作する
- **THEN** タブスワイプがその操作を奪わない

<a id="feed-09"></a>

### Requirement: FEED-09 入りきらないタブバー

フィードのタブバーは、すべてのタブにたどり着けることが見て分からなければならない（MUST）。入りきるかどうかは本数ではなく実際の幅で判定する。3本以下は従来どおり等分幅とする。入りきらないときは横スクロールにし、隠れたタブがある側の端をフェードで示す。末尾の「＋」は「▾」に差し替える。「▾」を押すと全タブの一覧が開き、タブの選択とタブのカスタマイズができる。横スクロールできる間はマウスホイールの縦回転で横に送り、端に達した回転はページの縦スクロールに使う。タブ設定のプレビューは、同じ幅であれば実際のタブバーと同じ並びと末尾ボタンで表示する。

#### Scenario: 入りきる本数

- **WHEN** タブが4本以上あるが、バーの幅に収まる
- **THEN** 各タブを伸ばしてバーいっぱいに並べる。末尾は「＋」とし、フェードと「▾」は出さない

#### Scenario: 入りきらない本数

- **WHEN** タブがバーの幅に収まらない
- **THEN** 末尾に「＋」の代わりに「▾」を出し、隠れたタブがある側の端をフェードさせる

#### Scenario: 一覧から選ぶ

- **WHEN** 「▾」を押し、一覧からタブを選ぶ
- **THEN** 一覧を閉じてそのタブへ移動し、選んだタブがバーの見える位置に来るようスクロールする。一覧では現在のタブに印を付ける

#### Scenario: 一覧からカスタマイズへ

- **WHEN** 一覧の末尾にあるカスタマイズ項目を選ぶ
- **THEN** 「＋」と同じく、今見ているフィードへ戻れる形でタブ設定を開く

#### Scenario: 一覧を閉じる

- **WHEN** 一覧を開いたまま、Escキーを押すか、一覧の外を押す
- **THEN** タブを切り替えずに一覧を閉じ、「▾」にフォーカスを戻す

#### Scenario: マウスホイール

- **WHEN** 横スクロールできるタブバーの上で、マウスホイールを縦に回す
- **THEN** タブバーを横に送る。バーが回転方向の端に達していれば、ページを縦にスクロールする

#### Scenario: 設定のプレビュー

- **WHEN** タブ設定でプレビューを表示する
- **THEN** 実際のタブバーと同じ規則で、等分・伸張・横スクロールと「＋」/「▾」を出し分ける。4本程度で収まる場合に左寄せにしない

<a id="feed-10"></a>

### Requirement: FEED-10 おすすめタブ

おすすめタブは、閲覧者の興味に近い投稿と、リアクションが集まった投稿を候補とし、新しい順に並べなければならない（MUST）。候補はトップ投稿に限り、返信は文脈なしに読めないため含めない。閲覧者本人の投稿は出さない。候補の判定はAppViewが行い、条件はAPI-10・API-11に従う。同じ人の投稿は1人1日1件までとし、その日の候補が複数あれば、興味に近い投稿を優先してその中で最も近いものを、興味に近い投稿が無ければ反応した人数が最も多いものを出す。それでも並ぶときは新しいものを出す。興味が分からない閲覧者にはリアクションが集まった投稿だけを出す。リアクション数などの件数は画面に出さない。こっそり・ミュート・成人向けの扱いはグローバルと同じとする。自分が投稿した直後の楽観表示はおすすめに出さない。

#### Scenario: 興味に近い投稿

- **WHEN** 閲覧者の興味に近い投稿が、まだリアクションを受けていない
- **THEN** おすすめに投稿時刻の位置で表示する

#### Scenario: リアクションが集まった投稿

- **WHEN** 閲覧者の興味とは離れているが、リアクションが集まった投稿がある
- **THEN** おすすめに投稿時刻の位置で表示する

#### Scenario: 1人が1日に何件も候補になる

- **WHEN** 同じ人の同じ日の投稿が3件とも候補になる
- **THEN** 1件だけを表示する。興味に近い投稿があれば、反応の数にかかわらずその中で最も近いものを選ぶ

#### Scenario: 未サインインの閲覧

- **WHEN** 未サインインでおすすめを開く
- **THEN** リアクションが集まった投稿だけを新しい順に表示し、未サインイン向けの案内も表示する

#### Scenario: 件数を見せない

- **WHEN** おすすめの投稿を表示する
- **THEN** リアクション数や興味の近さの値を表示しない

#### Scenario: 自分の新しい投稿

- **WHEN** おすすめを開いたまま投稿する
- **THEN** 楽観表示をおすすめに差し込まない

#### Scenario: 返信と自分の投稿

- **WHEN** リアクションが集まった返信や、閲覧者本人の投稿がある
- **THEN** おすすめには出さない

#### Scenario: 候補がない

- **WHEN** おすすめの候補が1件もない
- **THEN** おすすめに何が並ぶかを伝える空表示を出す

<a id="feed-11"></a>

### Requirement: FEED-11 返信を受け付けない投稿

閲覧者が返信できない投稿には、Nagiの返信ボタンを出してはならない（MUST NOT）。代わりに、返信を受け付けていないことを示す。返信できるかどうかはAppViewが返す値に従い、クライアントで判定しない。投稿者本人には常に返信ボタンを出す。

#### Scenario: 返信不可の投稿を他人が見る

- **WHEN** 「返信不可」で投稿された他人の投稿を表示する
- **THEN** 返信ボタンを出さず、返信を受け付けていないことを示す

#### Scenario: 自分の制限付き投稿

- **WHEN** 自分が「返信不可」で投稿した投稿を表示する
- **THEN** 返信ボタンを出し、続けて返信できる

<a id="feed-12"></a>

### Requirement: FEED-12 公開投稿詳細からの参加

クライアントは、認証状態の確認後、未ログインの閲覧者が取得できた公開投稿の詳細に、投稿と返信に続けてNagiの紹介を1つ表示しなければならない（MUST）。紹介はニュース・ブログの個別ページと共通とし、参加ボタンで既存のログイン・アカウント作成画面を開く。

#### Scenario: 未ログインで公開投稿を直接開く

- **WHEN** 未ログインの閲覧者が共有された公開投稿詳細のURLを開く
- **THEN** 投稿と返信を読め、会話の後ろにNagiの紹介と参加ボタンが表示される
- **AND** 参加ボタンから `/login` を開き、既存のログインとアカウント作成を選べる

#### Scenario: サインイン済みで公開投稿を直接開く

- **WHEN** サインイン済みの閲覧者が公開投稿詳細を開く
- **THEN** 認証の復元中と復元後のいずれも紹介を表示せず、既存の会話表示と操作を利用できる

#### Scenario: 公開投稿を確認できない

- **WHEN** 投稿が読み込み中、取得できない、こっそり、削除済み、または利用できない状態である
- **THEN** 紹介を表示せず、それぞれの既存の表示を保つ
